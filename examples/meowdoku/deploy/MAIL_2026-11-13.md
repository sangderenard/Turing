# Mail service (2026-11-13)

Owner's design, approved 2026-11-13 ("Yes, all recommended" after revision 1, "no low ports").

- Every person account has `<username>@stichka.duckdns.org`. Service accounts have none.
- Mail comes in on **47625** (never 25): aiosmtpd under `svc-mail`, STARTTLS with the Let's Encrypt certificate copied
  into `srv/state/secrets/tls-public/`. Only person mailboxes of the domain are accepted; nothing is relayed. Ordinary
  internet senders only try port 25, so their mail does not arrive: by design, the odd port is the filter.
- Mail goes out through a provider's submission port (587 STARTTLS or 465 TLS; 2525 works too), From the
  provider-verified address shown as "<name> via stichka.duckdns.org", **no Reply-To**; the text says answers go
  through the site. The credential is a JSON file `{"username": ..., "password": ...}`, read at submit time, never
  logged or stored in a row.
- Rows and bodies live in `srv/state/sql/mail.db` (`mail.py` is its one writer; ids join `accounts.db` `users.id`).
- The routing is the **Nodus email manager table**: contract prefix `mail` on `messenger.canvas` (port 47619), like
  `userlist` and `cron`. Tasks: `mail.file`, `mail.send`, `mail.sweep`. The table has its own cron tool (engine 7204,
  `jobs/mail/cron.table`: `mail.sweep` every 5 minutes). Engines: the receiver 7205, meowdoku-a 7206. Host: the
  `mail` instance, 7303. Requests carry a message id only.
- REST: `GET /api/mail/inbox`, `GET /api/mail/message`, `POST /api/mail/send`, `POST /api/mail/remove` (capability
  `message`; a send to an outside address also needs `mail_send`). Catalog group `mail` in speaktome, so the MCP tools
  `mail_inbox`, `mail_message`, `mail_send`, `mail_remove` are generated. Manual page `mail(5)`.
- `mail_send` is held by admin only by default. To let members send outside, add it to the member list in
  `authz_policy.json` (the list replaces the default: write member's whole list plus `mail_send`).
- Invitations: `mail.send_to_outside(mail_db, accounts_db, account=, to=, subject=, text=, config=,
  idempotency_key=, submit=)` is the call the invitation backend will use. Minting codes is not built here.
- Limits (`deploy/mail.json`): 10 MB a message, 20 recipients, 20 messages a minute per remote address, 200 MB a
  mailbox, 50 outgoing messages a day per account. v1 does not check SPF, DKIM or DMARC on inbound mail.

## Setup (2026-11-13, owner: "you can do most of this ... our firewall rules should be in the script that brings the thing up")

Done:
1. **Service Python**: `aiosmtpd==1.4.6` and `atpublic==9.0.0` installed into `C:/dev/Powershell/srv/python` with its own
   pip (`--no-deps`; `attrs` was already there). The pins are also in `requirements-service*.txt` for a re-provision.
2. **Account**: nothing to do. `svc-mail` in instances.json is a SERVICE IDENTITY in accounts.db, which the supervisor
   creates by itself (`ensure_service_user`), like every instance's account. The processes run as the Windows account
   the stack runs as (today the operator's own). When the stack moves to its own Windows account, that account needs
   read/write on `srv/state/sql/mail.db` and `srv/state/jobs/mail`, and read on `srv/state/secrets/tls-public`.
3. **Certificate**: `Copy-PublicCertificate.ps1` copied `fullchain.cer` and `cert.key` of the Posh-ACME order into
   `srv/state/secrets/tls-public/` (inherits the secrets folder: the operator only). `Start-Apache.ps1` runs it at
   every bring-up and copies only newer files, so a renewal reaches the receiver at the next start.
4. **Firewall**: declared, not hand-made. The `mail` instance declares `"firewall": [{"protocol": "TCP", "port": 47625,
   "program": ".../srv/python/python.exe"}]`; `Set-ServiceFirewall.ps1` makes each enabled instance's declaration one
   inbound Allow rule (group "SpeakToMe", that program and port only) and removes group rules no instance declares.
   `Start-Apache.ps1` and `Apache-Service.ps1 -Start/-Restart` run it. Changing a rule needs an elevated shell: a
   non-elevated bring-up only reports the missing rule and goes on.
5. **Instance**: the `mail` instance is enabled.

Still the owner's:
- **Provider**: the account, the verified sender, and the credential JSON where you choose; then `provider_host`,
  `provider_port`, `provider_security`, `from_address`, `credential_file` in `deploy/mail.json`. Until then outgoing
  mail waits (state `queued`, receipt "no provider_host is configured").
- **Elevation once**: the first rule needs one elevated run of `Set-ServiceFirewall.ps1` (or of `Apache-Service.ps1`).
- **Router**: forward TCP 47625 only if other hosts must reach it.
- **Go-live (a stop window)**: `deploy/Enable-MailTable.ps1` installs `jobs/mail/cron.table`, adds contract port 47619
  to the live canvas, and starts the stack again (Start-Apache.ps1, so the firewall and certificate steps run). It runs
  the live turing checkout, so this branch must have landed there first. Then check `srv/state/jobs/mail/cron.log`, the
  `mail` instance's line "receiving for @stichka.duckdns.org on 0.0.0.0:47625", and `GET /api/mail/inbox`.

No DNS change is needed: DuckDNS already answers `MX 50 stichka.duckdns.org`, and SPF does not apply while mail goes
out From the provider's address.
