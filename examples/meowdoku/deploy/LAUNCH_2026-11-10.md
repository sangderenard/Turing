## Administrative console (read-only viewer), 2026-11-10

What it is: the Nodus canvas host (`run_canvas.py`) can expose a READ-ONLY administrative console, and `frontend_shell.exe` can open a viewer window on it. It is the first step of the administrative console; opening and closing the window never disturbs the running graph.

Protocol summary: TCP on 127.0.0.1 only. The client sends HELLO with the shared token; the host then answers SNAPSHOT with the canvas file and one JSON state line. Anything else is answered `REFUSED read-only`, so the console is read-only by construction (the host has no command path in this phase).

Wiring: `instances.json` gives `nodus-messenger` `"console_port": 47612` (0 = ephemeral). For such an instance the supervisor writes a fresh token (`secrets.token_urlsafe(32)`) to `build/meowdoku/operator_credentials/<instance>.console.secret` at every launch, passes `--console-port <n> --console-token-file <path>` to `run_canvas.py`, parses `console_port` from the host's first JSON line, and records it in the `console_port` column of `service_instances` (`apache_supervisor.py --status` shows it). The token is per-run and readable by the operator account only (secrets dir restricted with icacls as in operators.py); the file is deleted when the instance stops or exits.

Open / close (both operator-gated like the other scripts; `-WhatIf` is supported after the gate):
- `.\Open-Console.ps1 -Instance nodus-messenger -User claude` reads `--status`, refuses if the instance is not running or has no console port, then starts `nodus/build-bridging/Release/frontend_shell.exe --attach=127.0.0.1:<port> --console-token-file=<token>` (the GUI uses the Torch build under the operator's account; the headless host is Torch-free), prints the PID and records it in `build/meowdoku/console-<instance>.pid`.
- `.\Close-Console.ps1 -Instance nodus-messenger -User claude` stops that PID if it is `frontend_shell.exe` and removes the pid file; it never touches the host.

Phase two (commands: a write path with its own authorization) comes later; nothing here accepts commands.

## Dev instance behind Apache (Stable server / Development server), 2026-11-10

Three different axes; do not mix them:
- **Stable server vs Development server** (this switch): two shared instances of the whole service. `meowdoku-a` (8766, route `a`, `"site": "stable"`) and `meowdoku-dev` (8768, 127.0.0.1 only, route `b`, `"site": "dev"`).
- **Dev page vs shader page**: the access tier and role (`dev_ui`, operator/admin). Unchanged by this.
- **Per-user leased servers**: not built.

How it works
- Only accounts holding `dev_ui` see the "Server" selector on `login.html` ("Stable server" / "Development server"). It calls `POST /api/route {site}`, which stores the choice (`account_prefs`, authz schema 2) and sets the `meowdoku_route` cookie; the page reloads. Login re-applies the stored choice for `dev_ui` accounts; everyone else, and logout, get route `a`. `GET /api/route` returns `route`, `routes`, `selected`, `preference`, `dev_available`.
- Apache (`apache/meowdoku-proxy.conf`, mirrored to `C:/Apache24/conf/`): every request is a `RewriteRule [P]`; cookie `meowdoku_route=b` goes to `https://127.0.0.1:8768` (and `wss://` for `/ws`, `/ws/spectate`), everything else to `balancer://meowdoku` (member a only). Route b is not a balancer member, so no anonymous request is balanced onto it. The conf change takes effect only on the next Apache start; it is NOT applied to the running Apache.
- The dev instance runs `--require-cap dev_ui`: any other principal gets 403 `this instance needs dev_ui` and a cookie reset to `a` (open: login.html/js, /api/account/login|logout|me, /api/whoami, /api/route). The cookie alone never grants access.
- Port 8767 (the other agent's dev server) is not involved: not proxied, not supervised.
- Accounts are shared; content and products are per server. The dev instance has its OWN state root `srv/state-dev` (content, web dir, logs, run files, job library) but the supervisor passes `--accounts-db` pointing at the top-level `srv/state/sql/accounts.db`: one identity, one session, one role set, one stored preference on both servers. The dev instance skips the startup lowering scan (the catalogue belongs to the database's owner) and runs no math lab worker.

- Then the instance builds its own products in that dir on first start (background lanes, port listens first): engine laws (predictor, policy, graph) and every fountain family with `--no-wasm` (GPU products only; no live retain receipt). Expect minutes of CPU on top of the live site; `--no-idle-train` and `--no-mathlab` keep the rest quiet.
