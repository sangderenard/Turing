what this measures

Every kernel here is one .ll file. The build machine compiled it natively and measured four tiers — two numpy baselines (what sympy.lambdify generates, where every operation allocates a fresh full-size temporary, and a hand-tuned in-place version with preallocated out= buffers: the strongest fair CPU-Python baseline), serial LLVM, and the deployment layer’s worker pool, sized by a live calibration probe. Those are the reference marks under each card, stamped with the machine that earned them.

The same .ll compiled to wasm32 is what your browser runs. Serial is one call on the main thread. Pooled mirrors the repository’s own browser shell (ensureTileWorkers): the module is compiled once, cloned to copy-in/copy-out Web Workers, and joined at a barrier — JavaScript coordination, because on a static page that is what WebAssembly parallelism is. No SharedArrayBuffer is assumed and no fast-math is enabled anywhere: native, wasm, and the in-page reference agree bit for bit, which is checked before any number is timed — the chaotic kernel would expose a single reordered multiply.

Correctness gates, then measurement, then the claim — the same order the compiler’s deployment stage enforces when it decides, per region and per backend, between serial, pooled, and GPU dispatch.
