2026-11-11 NODUS BROADCASTS A COUNTED-DOWN RESTART TO EVERY ADMIN; THE USER LIST AS A TABLE (MEASURED off-line; NOT YET LIVE):

Owner: "make us all friends with nodus for nodus to dispatch system events as broadcast, kicking off one tick of a
table that informs that there will be a restart in n seconds, click to interrupt, to all admin", then: "put in the
site's nodus canvas the userlist as a table that receives search terms, the table's finished output would be all the
identities that matched, then use that ... have the messaging system coordinate identities and work the nodus account
in messenger using tables with tools that perform very basic tasks, such as representing one identity".

Built:
- Countdown and interrupt: `instance_control.request(..., delay_s=N)`, `cancel(...)`, `due`, `to_announce`. The table
  gains `due_at`, `announced` and the state `cancelled`; a table made before today is rebuilt with its rows.
  Server: `POST /api/control/instances {…, delay}` and `POST /api/control/instances/cancel {id}`.
- The announcement: the supervisor asks the Nodus task table for ONE task, `system.broadcast`, when a countdown
  begins and again if it is interrupted (nodus `tools/task_request.py`, a one-off engine; top-level `system_events`
  in instances.json says which host, prefix and directory). The task worker performs it as messages from the system
  account (`svc-nodus-messenger`, shown as "Nodus"), type `approval_request`, subject `control:<request id>`.
- Friends: `messaging.system_contact` / `befriend_all`. The worker makes the system account a mutual contact of every
  account that is not a service account at its start, and of each recipient before telling it. An account that has
  blocked the system is left blocked and told nothing. The contact limits do not apply to the system.
- The user list as a table: prefix `userlist` on the canvas, performed by the task worker. `identity.search` takes
  search terms (`role:x`, `kind:person|service`, or text) and its output is every identity that matched;
  `identity.represent` gives one. `identity_tools.py`; both only read. A broadcast finds its audience by asking that
  table for one tick ("admin" is the search `role:admin`), then tells each identity it returned.
- Widget: a message whose subject kind is `control` and type `approval_request` shows an Interrupt button that calls
  the cancel route. The server decides whether the account may.

Measured (`tests/test_meowdoku_system_broadcast.py`, 7 tests; the last with NODUS_HEADLESS_TEST_DLL):
- SQL level: the system becomes a contact of the people, not of service accounts, and a block is respected; a
  broadcast reaches both admins and nobody else; search terms; a countdown is due only when it runs out, is
  interrupted once (409 the second time), and the interruption is announced once; an old table keeps its rows.
- REAL: a supervisor, a Nodus canvas host with `cron` and `userlist` ports, the task worker and a stand-in instance.
  A 20 s restart of `web` was announced to both admins ("There will be a restart of web in N seconds (request 1),
  asked by ann: maintenance"); the userlist table's request held `terms: ["role:admin"]` and its output was ann and
  bo; the broadcast's result said "audience found userlist table, contract ..."; interrupted by bo -> both admins
  told, `web` kept its pid, the request ended `cancelled`; a 4 s countdown then ran out and `web` got a new pid.

Hazards:
1. NOT LIVE. It needs the `userlist` port added to the live canvas, the installed worker arguments, and a restart
   of the whole stack (the supervisor itself changed). Until then the live control has no countdown and no cancel.
2. The Interrupt button is in `web/messenger-widget.js`, which the Studio lane is also editing (ten other hunks,
   uncommitted). The live web folder is an export; copying that one file would publish their unfinished changes too.
   So the button reaches the site only with their next export. The interrupt itself works through REST without it.
3. A message inserted by the worker does not wake a long poll held open in the server process (the wake-up is
   per process); a reader sees it when its poll returns, at most 25 s later.
4. The announcement is asked with a 5 s limit and is never retried; if Nodus or the worker is down the request is
   still performed and the log says the announcement was not made.
5. Another lane has raised the SpeakToMe REST contract to 3 in the working tree (`rest_api.py`, speaktome
   `routes.py`), uncommitted. None of this entry's commits include it.

Not done: no REST route hands the user list to people (deliberate: it lists accounts); the `everyone` audience is
not used by anything yet; the admin role's own use of the control from outside the local network is unmeasured.
