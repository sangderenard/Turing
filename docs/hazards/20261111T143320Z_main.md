2026-11-11 A TASK WORKER TAKES THE BAKING AND THE BACKUP OFF THE WEB SERVER (MEASURED off-line; NOT YET LIVE):

Owner: "there must be a tool or a worker responsible for taking development material and baking a static site copy
taking it off the plate of the server", then on backups: "Yes the binary backup will be a different policy. Also
we're not going to keep a huge rolling window".

Built:
- `examples/meowdoku/deploy/task_worker.py`: a process of its own. It joins the cron prefix as the host and performs
  `manual.hardcopy` and `state.backup`. It serves nothing and listens on nothing. At its own start it makes sure the
  manual's hard copy exists. Without a cron port it does that and idles.
- `examples/meowdoku/scheduled_tasks.py`: `handlers(...)` offers a task only when what it needs was given;
  `backup_state` calls the existing `state_backup.snapshot`.
- `examples/meowdoku/state_backup.py`: `snapshot(..., exclude=())` and `--exclude`, state-relative folders left out,
  recorded in the manifest as `excluded`.
- `examples/meowdoku/server.py`: the `--cron-port` / `--cron-jobs-dir` flags, the start-time bake and the cron host
  role are REMOVED. The web server serves; it no longer bakes or backs up.
- `deploy/instances.json`: new instance `task-worker` (kind `command`, account `svc-task-worker`, `cron_prefix: cron`,
  backups to `srv/backups`, keep 3, leaving out `content/marble_photos`); `meowdoku-a` no longer names the prefix.
- `deploy/cron.table`: `state.backup 30 9 * * * missed=once` (09:30 UTC nightly).
- `deploy/Restart-Stack.ps1`: exposure check, stop, wait for httpd to exit, start (the wait Stop-Apache lacks).

Decided by the owner: the snapshot leaves the binary photo files out (a different policy, not designed here) and the
window is small. Chosen here, easy to change in the instance's arguments: keep 3.

Measured:
- `tests/test_meowdoku_scheduled_tasks.py`: 9 passed with NODUS_HEADLESS_TEST_DLL set. A snapshot left
  `content/marble_photos/` out and kept a file whose name merely begins like it; three runs with keep 2 left two
  snapshots; `state_backup.verify` ok. The worker subprocess baked at start and stayed up without a cron port. The
  real cron round trip still performs `manual.hardcopy` through `scheduled_tasks.start`.
- `tests/test_meowdoku_state_backup.py`, `tests/test_meowdoku_apache_supervisor.py`: pass; the dry run lists
  `task-worker` with its full command.
- The worker starts under the service interpreter (`srv/python`): baked 31 pages into a scratch web folder.
- The live state is 3.1 GB in `content` (almost all `marble_photos`) against 27 MB for the last snapshot taken
  before those photos existed; that is why the photos are a separate policy.

Hazards:
1. NOT LIVE. The running server is still the cron host (started 14:10 UTC). Until a restart the installed
   `srv/state/jobs/cron/cron.table` must NOT gain the `state.backup` line: the running host has no such handler and
   would answer status 16 each night. Add the line and restart together.
2. After the restart the server no longer bakes at start. If the worker does not start, `/manual/` keeps whatever copy
   is on disk and is not refreshed; the supervisor's table shows the worker's state.
3. Two processes must never both host the cron prefix with different handler tables: a task handed to the one without
   the handler ends as "unknown task". Today exactly one instance names `cron_prefix`.
4. The supervisor creates the service account `svc-task-worker` on first start (as it does for every instance).

Not done: the full site export (`web_export.py`) is still run by hand; it belongs to this worker next, with the
question of which development material it may publish. An off-machine copy of the snapshots. The binary policy.
