2026-11-11 THE PART-BY-PART COMPILER TAKES A DREAM DOCUMENT IN AND WRITES ONE OUT (MEASURED, local Windows):

Owner: "the part by part compiler, it should produce a dream document as their enduring record" and then "So a dream
document goes in, the part by part compiler harness works on it, makes another dream document but that one can safely
have it's parts built individually".

Built:
- `src/compiler/dream_document.py`: `render_dream_document`, the missing inverse of `parse_dream_document`. The format
  had a scanner and no writer.
- `examples/meowdoku/source_divider.py`: `intake_dream` (a dream document as the source of a job) and
  `write_dream_record` (`<job>/record.dream`). CLI: `submit --dream FILE`; `recompose` now also writes the record.
  docs/DREAM_DOCUMENT.md describes both.

What "its parts built individually" rests on: each part's payload is the compiler's own cut,
`partition_authored_source(source, name)`, the same text `run_attempt` hands to `lower_ast_source_to_ssa`. The record
adds no cut of its own.

Measured:
- `tests/test_dream_document_render.py` (20 cases): round trip incl. the example document
  `examples/reversible_chip_simulator.dream`; payloads ending in CR, beginning with CRLF, empty; all 256 byte values
  under latin-1; ten refusals; a changed payload fails its sha256 sentinel on reading.
- `tests/test_meowdoku_source_divider.py`: 7 passed in 63.5 s.
  - A real wasm attempt's record: the lowering block's content hash equals the attempt's product_sha256.
  - Three chained functions: `step`'s part holds `RATE`, `double` and `step`, not `unused` nor the unused import; each
    part executes standing alone.
  - Dream in, dream out: the first record plus a GLSL shader block was given back to the divider. Second pass, every
    part its own block: `unused`, `double` and `step` each rebuilt to the SAME product bytes; the shader came out
    unchanged; the earlier pass's lowering and record blocks were dropped at intake.
- A real three-function job on js + c: 4 attempts in 29.6 s, record 30,878 bytes, 8 blocks
  (build/site-baked/example-record.dream).

Hazards:
1. First attempt at the record carried each function's authored span. That is NOT individually buildable (`step`
   named `double` without holding it). Replaced by the closure before anything was committed.
2. Shell heredocs here turn a doubled backslash into one: a test file written through one received a NUL byte and
   literal line breaks inside strings (git reported "Binary file matches"). Rewritten from a script file. Use the
   Write tool for any source containing backslashes.
3. A part's closure holds the functions it calls, so a second pass over a record divides those again; the record of
   the second pass has more parts than the first. The functions each part is FOR rebuild identically.

Not done: cross-block dependencies in a foreign dream document (pieces are cut within one block); the web intake page
does not take a dream document; the Nodus compile route (`divider_nodus_bridge.py`) does not write the record itself
(the record is written from the job's tables and product folders, whoever ran the attempts); `compile_sections` does
not interpret the c / llvm / fortran / wasm lowering blocks.
