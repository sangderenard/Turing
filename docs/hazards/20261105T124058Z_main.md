- Speed: the kernel run is 137 ms per batch of 32 (about 58 M multiply-adds, roughly 0.4 G/s); preparation adds 14-19 ms. The numpy-backend Python path evaluates the same 35 positions in 9.8 ms. Not wired into the search.
- Cause: the program is 130 calls to `matmul_double` (the batched `W @ cols` lowers to per-position index_select / matmul / index_set). `matmul_double` is the compensated (Kahan) inner product by design, with a strided right-hand operand; its correction chain does not vectorize at O3. This is the authored precision contract, not an emission fault. A faster evaluation needs a sanctioned faster GEMM lane; none was substituted here.
- Kernel bank gemm on the net's layer shapes (`open_blas_bank` + `LaunchCoordinator.launch("gemm", ...)`, first shape 32x117x2048): the parametric gemm compile now REFUSES on main with `region value 12 (Mul in function 'gemm') has no settled dtype in the tensor, specialization, node, descriptor, planned scalar types, its operands, its call actuals or domain` from `_build_shell_hierarchy_plan`. Value 12 is an index product in the authored kernel. The ValueError is not a `BankRefusal`, so the coordinator's reference fallback does not catch it. The August record had this kernel admitted at about 1 GF/s; no timing was obtained today.
- GPU GEMM lane (`glsl_blas_deployment.build_gemm_deployment_pair`): its products are standalone executables that fill A and B with synthetic values inside the shell and write C to a file. There is no in-process entry that accepts caller matrices, so it cannot evaluate the net. Nothing was built around it.
