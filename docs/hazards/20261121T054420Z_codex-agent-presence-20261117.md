# 2026-11-21 Explicit MCP cursor recovery (Windows, source only)

Base: Turing checkout `codex/agent-presence-20261117` at `c732f351f7570374be7fe06f1f400eb8576b414c` before this change. Paired SpeakToMe checkout: `codex/agent-scratch-mcp-20261116`.

A graph cursor belongs to one account and has a one-hour inactive lifetime. The MCP process stores its cursor id only in memory. If that process exits, a replacement process cannot enter (one cursor already exists) or leave (it does not know the id). The Research/Development case `529834940cf9431e92ff6ff23e64d6a6` fixes this by allowing a dev_ui-authenticated account to read only its current cursor id/revision, then explicitly close it through the existing revision-guarded close path. A second enter still fails. No server or permission change was made live.

Turing adds `CursorStore.current(owner)`; the paired SpeakToMe REST route exposes GET `/api/living-data/sessions/current`, and its MCP leave verb uses that only when no cursor id exists in the process. The GET discloses no other owner's session. A concurrent move yields 409 on close and is not retried automatically.

With `SPEAKTOME_REPO` pointing to the paired checkout, `C:\dev\Powershell\srv\python\python.exe -m pytest -q tests/test_living_data_cursor.py -p no:cacheprovider`: 4 passed, 2 warnings (optional Nodus tensor core disconnected and cffi imp deprecation). This is a focused Living Data/HTTP check, not a compiler or numerical gate. Live completion requires independent reviews to land both repositories and owner-controlled connector/service activation, followed by an account process-loss retest.
