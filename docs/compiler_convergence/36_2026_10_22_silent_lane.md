## 1. S1 closed: tuple displays are born (lanes plan A1)

**Program.** `t = (n + 1, n + 2, n * 3); return len(t)` returned 0 for
every input, Python says 3, with 0 concordance findings. Minimal form:
`return len((n, n + 1))`. The same lost record made these silently wrong at
`main` (observed, scratch): `t[1]` guarding `len(t)`; `a, b = t` beside
`len(t)`; a tuple of a list's `len` taken before an append; a tuple rebound
in a loop; `len` of a nested tuple. An all-constant tuple was folded and
was correct.

**Records that disagree.** `SOURCE_AGGREGATE_LAYOUT` for the tuple (k
members) versus the module's writers of that sequence identity (none). The
root declared the tuple's resident storage and read its length cell
(`ssa_sequence_length`), but nothing cleared it or appended to it, so the
read saw the frame's zeroed cell.

**Pass that lost it.** `_list_literal_mutations` births lists and sets
only (it filtered on `ast.List`/`ast.Set` and on a layout kind of list or
set). Once tuples are born, `_static_sequence_capacity_survey` had no bound
for them (it counts `ast.List` displays only), so the product refused the
arena ("no proven capacity"), which is loud.

**Fix.** A tuple display is born like a list display: one clear, then one
append per layout member. Nothing grows a tuple, so its member count bounds
it, even when it escapes into a call. The audit now reports a display with
a non-empty layout whose length is read while no instruction writes its
sequence (`display-length-unborn`). On `main`'s lowering of
`len((n, n + 1))` it reports that one finding.

The doc 33 note that the members' producer region is owned by a later
conditional did not reproduce at `main`: `t = (n > 0, n > 2, n > 4)` with
`if t[1]:` before `len(t)` returns Python's value after the birth
(observed).

**Corpus.** `c260_tuple_display_len` (bool and int tuples, unpacking,
iteration, a `t[1]` guard; loud at `main`) and `c261_tuple_len_silent`
(silently wrong at `main`, PASS now). Fuzz snippets: a computed tuple's
`len` and projection, and a loop over a bool tuple.

**What became loud instead of silent** (observed; each matches the list
form at `main`, so each is an existing frontier item, not a new one):
- a tuple rebound inside a loop: PRODUCT-REFUSES, as `xs = [i, i + 1]` in
  a loop does (C2);
- a nested tuple `((n, n + 1), (n + 2,))`: "no source cell" for the
  SEQUENCE_MUTATION block, as the nested list does (C6);
- a display that repeats a producer, `(m, m, 9)`: "lacks one exact element
  producer", as `[m, m, 9]` does (measured by the A0 thread);
- a member that projects another structural tuple, `(t[1], n, 9)`: the
  layout member is the Subscript's id while the `elts` edge names the
  forwarded producer (measured by the A0 thread; loud for lists too).

**New frontier finding, loud at `main` and here.** A helper returning a
tuple, `p = pair(n); len(p) + p[1]`, fails C compilation: the call's
aggregate pointer array is typed `double *` for `int64_t` members. This
belongs with B1 (return surface).

## 2. W2 closed: concatenations (four writers, one family)

W2 (found by the coverage march's fuzz snippets) was `d = {1: 5, 2: 4};
d[3] = n; xs = [1, 2] + [n, 8]`, after which `xs[2]` read 0. Minimizing it
showed four writers that each made a list concatenation wrong without an
audit finding. Three were silent at `main` (observed, scratch and corpus).

**1. Placement (c262).** The concat is a table region operation (reset,
then one `append_slice` per operand). Its region was placed where its
members start (`_member_completion_position`), so the `+` at column 9 sorted
before the `[n, 8]` display at column 18, whose birth (clear, appends) is
placed at its own start. With a dict store's region in the same function
the copy was observed to come first and read an empty `[n, 8]`. The A0
thread found the same writer independently (fuzzer p16_29, PR #786, commit
a4c29be9: a member reading a display operand completes where that display
ends). This branch carries that change verbatim instead of its own broader
rule, so the two PRs merge cleanly. Records: the display's birth
(`ssa_sequence_clear` of sequence 12) and the copy naming it
(`append_slice`, `source_sequence_id` 12), in that order in one block. The
audit now reports `display-read-before-birth` when a slice copy reads a
display before its birth in the same block (one finding on `main`'s
placement of c262's shape, 0 after).

**2. Row type (c264).** `xs = [1, 2] + [n, 8]; return xs[2]` returned
`3.0` (TYPE). The concat's arena has no writer but slice appends, so its
row stayed `unknown` and scalar settlement typed it float64 (trapped:
`_sequence_descriptor` → `external_value` mints `unknown`, then
`ir_indexing._propagate_scalar_dtypes` writes float64). Rule: a slice
append is a row writer; the source's row type refines the destination's,
as an append's stored value does (`_emit_sequence_append_slice`).

**3. Nested bounds (c263).** `ws = [n] + [1, 2] + [n * 2]` gave
`len(ws) == 2` for 4, and `ys = [7, 8] + xs; zs = ys + [n]` lost rows. The
capacity survey bounded a concat only when both operands carried
`aggregate_kind == "list"`; a concat (an `Add`) carries none, so a concat of
a concat had no bound and took the planner's elementwise extent. Rule: a
bounded concatenation is a list operand; the bounds settle to a fixed point.

**4. Unbounded concats.** `xs` grown in a loop, then `ys = [7] + xs`:
`len(ys)` read 1 for 4 at `main`. A concat no bound covers was neither
bounded nor DYNAMIC. Rule: a concatenation is born in its function and
holds its operands' rows; with no proven bound it is DYNAMIC. It is now
**loud**: `dynamic-growth-unavailable ... this operation must support arena
replacement`, because `append_slice` has no DYNAMIC growth protocol yet.
That is the new frontier item (a lowering, Lane C).

Fuzz snippets: the W2 shape (dict store beside a concat) and a three-way
concat.

## 3. C13 made loud: a list mixing int and float rows

**Program.** `ys = [n]; ys.append(n * 0.5); return ys[1]` and
`ys = [1 * n, 2.5 * n]; return sum(ys)` (lanes plan C13, found by Lane C).
At `main` the second returned 3.0 for 3.5 (n = 1). The first exported
nothing (`Ret []`). Both had 0 audit findings.

**Records that disagree.** The arena's row type is int64, taken from its
first row. The appended row's value is float64. The append helper's row
formal is int64, and the call input adapter
(`ssa_call_input_adapters`, the `logical_scalar_conversion` branch) minted a
float64 to int64 `Cast` (`concordant_call_input_conversion`) to make them
agree.

**Rule.** Python never converts a float to an int implicitly. A call input
conversion from a floating actual to an integer or bool formal is refused
by name (`call input conversion would truncate`). Widening conversions are
unchanged.

**Not lowered.** A list whose rows have different scalar classes needs a
per-row class (or a float64 arena plus the int rows' class) to be exact:
`ys[0]` must stay `int` while `sum(ys)` is `float`. That is a Lane C
lowering, still open. Test: `tests/test_mixed_row_list_refusal.py`.

## 4. C14 closed: a loop over an inline comprehension

**Program.** `for y in [x * n for x in xs]: t += y` with `xs` a folded
literal (c265) returned 0. It was silent at `main`, where the unrolled
comprehension had no birth at all.

This builds on Lane C's b1da6a5e (an unrolled comprehension over a folded
list is born like a display), which this branch carries unchanged. That
commit closed the named form (`ys = [...]; for y in ys`). The inline form
still read 0.

**Records that disagree.** The loop reads the iterable's length
(`resident_iterable_length`, sequence 11) in the entry block. The
comprehension's birth (clear, three appends) was installed in the loop
body.

**Writer.** `_install_lexical_sequence_mutations` kept a private copy of
loop containment, and that copy used the `for` statement's whole span. The
birth is authored on the `for` line, so the copy put it inside the loop.
The p3_46 rule (`_loop_body_line_span`: a `for` loop's iterations are its
body lines) existed but had not reached this copy.

**Rule.** There is one containment rule; this copy now calls it. The other
`loop.lineno <= line <= loop.end_lineno` tests sit in the capacity survey,
where they mark an append as loop-grown. A whole span is the conservative
direction there (a wrong guess makes the arena DYNAMIC, not short), so they
are unchanged.

Fuzz snippet: a loop over an inline comprehension of a literal.

## 5. C12 closed: a comprehension result mutated afterwards

**Program.** `ys = [x * n for x in xs]; ys.append(n)` with `xs` a folded
literal, then `len(ys) * 100 + sum(ys)` (c266). `main` returned 0.0 (the
comprehension had no birth). With Lane C's birth (b1da6a5e) it returned
306 for 407. The audit was clean both times.

Three records were lost, and each fix was measured on its own:

1. **The append's node.** Loop evaporation (`evaporate_unrolled_loops`)
   prunes every node that is not an ancestor of a root. The append has no
   consumer, so its node was deleted. Its retained mutation record named a
   missing node, so the effect had no position and was placed after the
   reads. **Rule:** a node a retained sequence mutation names is live. The
   dead-call pruning already follows this rule (scratch c_s5).
2. **The arena's capacity.** The capacity survey counts later appends only
   for local lists, and an unrolled comprehension was not one. The arena
   took the planner's extent (3,), so the fourth append found it full and
   its status was dropped (len 3). **Rule:** an unrolled list comprehension
   is a local list of its materialized rows. Without this rule, after fix 3
   the product refuses by name ("no proven capacity").
3. **The reduction's extent.** The comprehension's descriptor proved shape
   `(len(xs),)` from its iterable, so `sum` reduced over a static three
   rows of four (406 for 407). **Rule:** a mutated collection's leading
   extent belongs to its length cell, as it does for a dynamic iterable.

**Audit.** The new finding `static-extent-of-grown-sequence` fires when a
reduction reads a static extent below the number of appends the module
makes to that sequence. It fired on c266 with fix 3 held back.

**Still loud.** A set comprehension followed by `add` refuses by name
("no proven capacity"). It was loud at `main` too.

Corpus c266 (append, then `len`, `sum` and an index) and c267 (a loop of
appends after a comprehension, with `max`). Fuzz snippet: a comprehension
and then an append.

## 8. An indexed store dropped out of the source-call order

**Program.** `xs0 = [5, n, 0]; xs0[1] = 8; xs0[0] += n; xs1 = [7, 7];
push(xs1, n); push(xs1, 2)`, then `(xs0[0] + xs0[1]) + (len(xs1) * 100 +
xs1[2] + xs1[3])` (c280, fuzzer p28_37, FUZZ_EXT=3 seed 28). At `main`
ca9668a4 it returned 1220 for 409 with a clean audit, and with
`xs1 = []` it segfaulted (a null heap read).

**Lost record.** PR #786's call-order rule in
`_sequence_effect_read_edges` chains effects and source calls in source
order. Indexed stores were not members of that chain. The reducer fused
the augmented store's `xs0[0] + n` (line 3) with the reads of `xs1` after
both pushes (line 7). The store sits at line 3, so that fused region was
scheduled before the calls, and the reads saw neither push. Removing either
store or one push hid the fault.

**Rule.** An indexed store is an in-place effect lowered where it is
authored, so it keeps its place in the order. The store that an augmented
assignment writes has no location of its own, so it completes where its
value does.

**Audit.** None. Reading a list before a call that grows it is legal
Python, so the module alone cannot tell this order is wrong.

**Measured** at 7b3ec6e1: corpus 185/185 PASS. Fuzz seed 30 (base, 40)
gave 40 PASS. Seed 28 (FUZZ_EXT=3, 60) gave 58 PASS, 1 LOUD (LOUD at
`main` too) and 1 WRONG. The WRONG is p28_34, which is lanes plan C15 (a
comprehension and then `sort()` of another list; Lane C's item, WRONG at
`main`). Gate: the failure names are identical to a fresh gate of `main`
ca9668a4 in all four parts (aa 96, ab 20, ac 57, rec 39).

## 10. An unrolled comprehension dropped out of the source-call order

**Program.** `ys0 = [x0 * n for x0 in [4, 0, 8]]; xs1 = [3]; push(xs1,
n)`, then `sum(ys0) * 10 + len(xs1) * 100 + xs1[1]` (c283). The program
came from fuzzer p32_55 (FUZZ_EXT=3, seed 32) at `main` bbf81da8, which
crashed natively. With `xs1 = []` it is a null read (c284). With `xs1 =
[3]` it returned 100 for 200 with a clean audit.

**Lost record.** An unrolled comprehension is born where it is authored:
one clear, then one append per row. It was not a member of the order in
`_sequence_effect_read_edges`. The reducer fused a row's `x0 * n` with
`len(xs1) * 100`, and the birth placed that region before the push.

**Rule.** An unrolled comprehension's birth keeps its place in the order,
as a call does. Section 13 widens this to every comprehension.

## 11. Set comprehensions grown by `add`, and a set grown by a helper

**Programs.**
- `ys = {x * n for x in [4, 0, 8]}; ys.add(n + 5)` was refused with
  "dynamic-growth-unavailable" (c285, c286).
- `def add1(s: set[int], v: int): s.add(v)` was refused with "sequence
  contract concordance disagreement ... unique/1 ... duplicates/1" (c288,
  c289). This happened for a set display, a set comprehension, and
  `set()`.

Both were LOUD at `main`.

**Lost records.**
- The capacity survey treats a set display as a local set, but an
  unrolled set comprehension (born the same way) was not one.
- The added int carries the ProgramABI identity `builtins.int`. That made
  the parameter a record sequence, whose declaration said `duplicates`
  over the authored `set` contract.

**Rules.**
- A set comprehension that a later effect grows is a local set. One that
  nothing grows keeps its exact row descriptor. Putting it on the dynamic
  contract read 902 for 101 when rows repeat (c287 guards this).
- A record sequence keeps the row policy its authored contract committed.
  The record names only its rows.

## 12. A returned read of a grown list, and reads before a later effect

**Programs.**
- `xs = [3, n]; xs.append(2); return xs[2]` returned **nothing**: the
  root's `Ret` was empty (c310).
- `a = xs[1]; xs[1] = 9; return a + 0` returned 9 (c311).
- The same happened with `pop` (c312), a mutating call (c313), `sort`
  (c314), `insert` (c315), a store or pop inside an `if` (c316, c317), a
  negative index before `append` (c318), and a dynamic index (c319).

All were WRONG at `main` with a clean audit.

**Lost records.**
- A row read that no region owns is loaded where its value is first asked
  for. A bare returned read is never asked for, so output resolution
  skipped it.
- Effects were ordered only before the reads after them. Nothing kept an
  earlier read before a later effect, and the lazy load ran at the read's
  consumer, after the effect.

**Rules.**
- A returned row read is control-owned, as a returned length is.
- A read that ends before an effect on its receiver starts precedes that
  effect. For an effect inside a branch, that is the enclosing `if`.
- `_sequence_effect_read_edges` records these edges
  (`sequence_read_before_effect_edges`). The lowering loads such a read
  before the region or control effect it precedes, or at the `if` it
  precedes.

A read before an effect inside a loop still keeps its consumer placement,
because a loop block names no graph node. The probes in that shape pass.

**Audit.** New finding `source-output-unreturned`: the function's
`source_output_value_ids` name a value, but one of its `Ret`s returns
none. It fires on c310 when the fix is removed.

## 14. R1: an order edge against a value edge (tire region cycle)

node-level cycle in `balloon_tire_vector_step`. The stores `output[:, :,

## 15. A fixed-capacity write that finds no room is loud (takeover rule 10)

**Program.** Lane E's E10 (doc 37, c303): a callee list whose capacity
cell stayed 0. Every append reported "full" into a status nobody reads.

**Lost record.** `ir_sequence_tables` raised validation error 75 only for
a fixed fill. A fixed `append`, `add`, `insert`, `insert_at`,
`append_slice`, `prepend`, `pack_bits`, `prepend_packed_bytes` and the
record child copy returned status 2 and nothing read it, so any wrong
capacity was silent.

**Rule.** A FIXED write that finds no room raises error 75
(`_raise_fixed_capacity_exhausted`). Only the DYNAMIC protocol's insert
step (`_lower_dynamic_sequence_mutation`, `raise_when_full=False`) reports
"full" without raising, because its caller reserves and retries.

**What had relied on it.** The corpus then failed in two programs, c271
and c272. Both call a callee that binds a list to branch displays
(`t = [n, 1]` or `t = [5, 6]`). The display `[5, 6]` is a graph Constant
whose id is also the column of the callee's sequence, so the frame
binding treated that formal as a caller literal. The caller passed a
two-element constant as the arena. The wrapper publishes capacities only
for frame-owned storage, so the capacity stayed 0 and both appends went
"full". The answers were right only because that arena was dead (the
merged list is built from the arms' scalars).
Rule: a callee formal that names a cell of one of the callee's sequences
is frame storage, never a literal (`fortran_c_shell`, default literals
of a linked call). Corpus c331, fuzz helper `branchpair`.

## 16. `d.get` in a loop: hoisted to entry, and typed float64

**Program.** `d = {}; for i in range(n): d[i % 2] = d.get(i % 2, 0) + 5`,
then `return d[0] + len(d)`. At `main` n=3 returned 7.0 (Python: 12), n=1
a float. Audit: "entry#13 Call reads a value defined at loop_body". Lane
C's C17 fix (65623aee) does not cover it.

**Lost records.**
- Placement: the `get` fed only a numerical region, so it was neither
  control-consumed nor region-owned. The SSA prologue emitted it at
  function entry, before the literal's clear and outside the loop, with
  its key read before definition.
- Class: `get` had no rule in `_planned_scalar_dtypes`, so its result
  entered the `+ 5` region at the float64 domain default. An empty table
  took float64 rows; a table with int literals refused the float store
  (LOUD). A loop's carried `d` (a LoopResult of the body's store) was read
  as a comprehension result, so `d[0]` after the loop was float64 in a
  callee, and the caller kept a float result the callee no longer had.

**Rules.**
- A keyed read of a sequence the control tree mutates is placed at its
  authored node, as memberships already were. Only a read of an unmutated
  sequence may stay at entry.
- `d.get(k, default)` has the join of the table's element class and the
  default's. The receiver may be the table, a store's version of it, or a
  loop's carried version. A table whose only writers are fed by the read
  has no element class until the read has one; in a second phase, after
  every other proof, the default's class seeds it. A later disagreement is
  refused by the row concordance.
- A carried LoopResult holds its body value's element and scalar class.

Corpus c330, fuzz snippets (dict counted through `get` in a loop, and
`get` after a store).

## 19. A tuple swap of list cells

**Program.** `xs = [n, 3, 2]; xs[0], xs[2] = xs[2], xs[0]` then `return
xs[0] * 100 + xs[2]`. At `main` it returned 202 for 200 + n.

**Wrong record.** A tuple assignment's targets are authored before its
values, so the store `xs[0] = ...` starts before the read `xs[0]` on the
right. Section 12's rule (a read that ends before an effect starts comes
first) ordered nothing. The read was placed after the store, and both
cells held 2.

**Rule.** Python evaluates the whole right side first, and the graph says
so: the read's base is the version the store consumes. Outside loops and
branches, a read of the version an indexed store consumes precedes that
store (`_sequence_effect_read_edges`). Corpus c333.

## 20. A store through a projection, `m[1][0] = n`

**Program.** `m = [[n, 4], [5, 6]]; m[1][0] += n`. At `main` the store
was silently lost: `_mutated_sequence_node_ids` walked a store's base
only to a collection, and the base here is the projection `m[1]`, so the
fold replaced `m` by its initializer.

**Rule.** The store-base walk follows an indexed base to its own base, so
`m` is mutated. The program is now LOUD ("control_block: no source cell",
Lane C's C6), not silent. Lowering nested stores stays Lane C's item.

## 21. `[n] * k`, and reductions over list literals

**Programs and wrong records** (all at `main`):
- `xs = [n] * 3` filled zeros. The fill policy carried only literal
  members, so a runtime member became the default literal.
- With the fill fixed, `xs = [n] * 3; xs[1] = 3` was refused: the control
  function stored the rows as float64 and the regions read int64 ("1
  incompatible final physical call inputs"). The descriptor had no class
  for a runtime member.
- `sum(xs)` over `[n] * 3` returned a float. The posted descriptor of
  `sum` over a source list carried the list's float64 domain default,
  which overrode the int64 the source proves.
- `sum([1, 1, 1])` (and `xs = [1] * 3; sum(xs)`) returned 1 * 10 + n. The
  region's `Const` line for the list literal had no value record (it is
  neither a region node nor a capture), so it lowered as a scalar. Its
  own record also squeezed the padded DomainNode (1, 1, 1) to a scalar.
  The audit found this one at `main` (one occurrence finding).
- `min([3, 1, 4]) + n` returned a 3-wide row of zeros. The structural
  fold turned `min` into the literal 1 but kept the reduction's tensor
  shape (3,).

**Rules.**
- A runtime fill member is encoded `("value_id", id)` and the fill helper
  receives that value.
- The rows hold the class the regions prove for the sequence, else the
  member's.
- In `_value_shape_dtype`, a class the source proves
  (`_planned_scalar_dtypes`) stands; the posted descriptor speaks only
  where the source proves none. A replication's element is its single
  collection operand's element.
- A list/tuple literal of scalars has its own extent. A materialised
  constant with a non-scalar extent carries its value record.
- A folded literal's extent is the literal's own.

Corpus c334, c335, c336.

## 22. `len(d)` after `del d[k]`

**Program.** `d = {1: n, 2: 3}; del d[1]; return len(d) * 1000 + n`. At
`main` it returned 2000 + n.

**Wrong records.** Two.
- `len` loaded the length cell, which still counts the tombstoned row
  (a deletion clears a live flag and leaves the row resident).
- The live-flag arena had no capacity bound, so the wrapper allocated one
  flag. The second row's flag was written past it: an out-of-bounds
  write in C, at `main`, for every dict with a deletion and more than one
  row.

**Rules.** A table that retains deleted rows has the length of its live
rows (`lower_sequence_live_length`, a counting helper). Live flags are
bounded like a column (`ssa_storage_requirements`). Corpus c337, c338.

## 23. A membership query after `del d[k]`

**Program.** `d = {1: n, 2: 4}; del d[1]` beside list work, then
`int(1 in d)` (fuzz p81_13). At `main` it returned 1397 for 397.

**Wrong record.** A dict key deletion is not a control effect. It rides
as a pre-operation of the region after it in value order. The membership
query that follows it in source was placed before that region, ordered
only by run position (a write after a read), so it found the deleted key.

**Rule.** A table query whose result follows a deletion of that table
reads after the region that carries the deletion. Where that region also
needs the query's value, the order is a cycle and lowering refuses. That
is the same refusal the simpler shapes (`del d[1]` then `1 in d` alone)
already gave at `main`, so this family is now loud everywhere. Lowering
it right needs the deletion to be its own control effect, as a list's
`del xs[i]` already is: a planner item.

## 24. `d.get` after a keyed store in an unrolled loop (plan C4)

**Program.** `d = {}; for i in range(4): d[i % 2] = d.get(i % 2, 0) + n`
then `return d[0] * 10 + d[1]` (Lane C, at `main` 4a0f5452). It returned
-33 for -66, and the audit was clean.

**Wrong record.** `range(4)` unrolls. Each `get` is a lookup query and
each store rides on a region. The four queries sat together in the run
ahead of the first store region, and a query was ordered against the
store regions only by run position: a write after the latest read. So
every `get` read the empty table.

**Rule.** As in section 23, a table query whose result follows a keyed
store or a deletion of that table reads after the region that carries
it. Such a query also takes no write-after-read edge to that region: the
write follows the latest reader that does not, else the last write.
Corpus c380 (two dicts, with defaults 0 and 1): WRONG at `main` d5e0e321,
PASS here.

## 25. An append to a branch join, beside a comprehension

**Program.** `if n > 6: t0 = [n, 3] else: t0 = [8, n]`, `t0.append(6)`,
then a comprehension (fuzz p85_1 and p49_49). At `main` 4a0f5452,
`len(t0)` was 2 and `t0[2]` was 0.

**Wrong record.** The join's list is born at the join: a clear, then one
append per member. In the run that birth sat after the append, because
the comprehension's place in the source-call order (section 10) pulled
the append ahead of it. The write-after-write rule then ordered the birth
after the append, so the clear erased it. The audit was clean.

**Rule.** An access of an arena follows its birth, wherever the birth sits
in the run. A birth takes no write-after-access edge from an access it
precedes: nothing existed to write. This is the write-after-write half of
the existing rule for reads (fuzz p3_54). Corpus c339.

## 26. A nested store beside a comprehension (now loud)

**Program.** `for y in [x * n for x in [6, 3]]: t += y`, then
`m = [[n, 5], [5, 5]]; m[1][0] = n` (fuzz p85_45, p86_17). `m[1][0]`
read 5 at `main` 4a0f5452.

**Wrong record.** Loop evaporation pruned nodes by ancestry. The store
sat outside every evaporated loop body but shared an ancestor with the
comprehension, so it was pruned with the loop.

**Rule.** An indexed store outside the evaporated loop bodies is live.
The program now stops loudly at the same place the store alone does
(section 20); nested stores belong to Lane C's C6.

## 27. One helper called with a display list and a grown list

**Program.** `head(xs0)` with `xs0 = [n, 1]`, then `head(xs2)` with
`xs2 = [n, 2, 6]; xs2.append(0)` (fuzz p86_42, which also segfaulted).
At `main` 4a0f5452 `head(xs0)` read 0, so `-326` came back as `-26`.

**Wrong record.** Callsite specialization made two copies of `head`.
The first binds `xs` by its display members (`xs[0]` is a formal); the
second binds `xs` whole, as grown storage. Both copies had empty literal
and tensor contracts, so both were lowered as `x__head`. The second
lowering reused the first symbol, and the first call bound minted frame
slots that nothing filled. With the calls swapped, the program stopped
on an unknown callee instead.

**Rule.** A member-bound aggregate (`planner_aggregate_descriptors`) is
part of the callsite contract that names the symbol. A reused symbol
must also have the same input frame (each input's binding, aggregate
parent and path), or it is refused. With only the second rule, c381
stops with `ConcordanceRefusal` instead of answering wrong. Corpus c381.

## 29. A loop over a tuple display; an enumerate start read before it exists

## 30. A call that stores into its list argument

**Swap before a later row read (wrong, audit clean).**
`xs2 = [n, 6]; h2 = head(xs2); swap(xs2)`, then `xs2[0] * 10 + xs2[1]`,
after a `d.get` store and a comprehension loop (fuzz p92_28). At main
24a30c2b this gave -329 for -239, with a clean audit. **Wrong record.**
In `_schedule_loop_callsites`, `sequence_accesses` gave a
`__plan_callsite_N__` statement no arena access, so no RAW edge ordered
the region reading `xs2[0]` after the `swap` call, and a value edge from
the table work placed that read first. `xs2[1]` was right only by run
position. **Rule.** A call writes every arena of its run that it
receives as an argument: it follows that arena's last write, and later
readers follow it (RAW). Which callee stores is not known at this pass,
so a call write takes no WAR edge from an earlier reader (a read-only
`width(ys)` inside the region that reads `ys[-1]`, c193, would otherwise
close a cycle), and a call fed an arena a later statement produces keeps
only its value edge. Corpus c384.

## 31. A helper reads a list another call stored into

**Swap, then head (wrong, audit clean).** `xs = [n, 6]; swap(xs); return
head(xs)` returned `n`, not 6, at main 24a30c2b. **Wrong record.**
`_aggregate_binds_by_member` bound `head` to the display's members,
because it counted only the caller's own mutations
(`include_call_escapes=False`) and `head`'s, not `swap`'s store into the
same storage. **Rule.** An aggregate that also escapes into another call
is bound whole, as its storage. Corpus c385.

**Calls that provably store (plan item, WAR).** `fortran_c_shell` now
gives `_schedule_loop_callsites` the caller arguments each callee stores
into (`_mutated_sequence_node_ids` of the callee holds the formal's
Input). A storing call is a full writer of those arenas, WAR edges
included; a call known not to store writes nothing; a call with no child
graph keeps the may-write rule of section 30. Every arena argument is a
read of the call, so a whole-bound `head(xs)` before `swap(xs)` stays
before it. No program was found where the missing WAR edge alone gave a
wrong answer; the edge is there for the case.

## 32. Two displays share a member (loud family "lexical_reads ... fork")

**Refused, not wrong.** `s0 = {n, 5}; s0.add(7); xs1 = [6, n, -3];
xs1.append(1)` was refused with "control_block: no source cell for
(lexical_reads ... fork ...)". It was the largest loud family in fuzz
(10 of 13 LOUD in seeds 102-105). **Wrong record.** `post_control_program`
keys a sequence mutation's CONTROL_BLOCK row by its owner, and a display
member's birth is owned by the member's producer (`effect_node_id`),
which is not unique: the set's `add` of `n` and the list's `append` of
`n` posted two facts on one row. The second was refused as a revision
with no new cause. Two list displays sharing `n` already posted one
equal fact there, so they compiled. **Rule.** A display member birth's
fact is "display_member"; the block itself names the sequence, kind
and member. Corpus c386. Seven fork-refused fuzz programs from seeds
94-105 now compile and match Python; the others moved to other loud
refusals or remain fork-refused.

**Left loud on purpose.** Every fork refusal still standing is a nested
display (`m = [[n, 6], [0, 2]]` then a store or append into `m`): the
inner display's `clear` and the outer display's member birth share the
inner display's cell. Posting both as one "display birth" fact made
`m2[1] = [n, 1]` compile to a wrong answer (audit flagged), so that
collision stays a refusal. Nested stores are Lane C's C6.
