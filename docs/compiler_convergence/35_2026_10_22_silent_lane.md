## 1. S1 closed: tuple displays are born (lanes plan A1)

**Program.** `t = (n + 1, n + 2, n * 3); return len(t)` returned 0 for
every input, Python says 3, with 0 concordance findings. Minimal form:
`return len((n, n + 1))`. The same lost record made these silently wrong at
`main` (observed, scratch): `t[1]` guarding `len(t)`; `a, b = t` beside
`len(t)`; a tuple of a list's `len` taken before an append; a tuple rebound
in a loop; `len` of a nested tuple. An all-constant tuple was folded and
was correct.

**Records that disagree.** `SOURCE_AGGREGATE_LAYOUT` for the tuple (k
members) versus the module's writers of that sequence identity (none). The
root declared the tuple's resident storage and read its length cell
(`ssa_sequence_length`), but nothing cleared it or appended to it, so the
read saw the frame's zeroed cell.

**Pass that lost it.** `_list_literal_mutations` births lists and sets
only (it filtered on `ast.List`/`ast.Set` and on a layout kind of list or
set). Once tuples are born, `_static_sequence_capacity_survey` had no bound
for them (it counts `ast.List` displays only), so the product refused the
arena ("no proven capacity"), which is loud.

**Fix.** A tuple display is born like a list display: one clear, then one
append per layout member. Nothing grows a tuple, so its member count bounds
it, even when it escapes into a call. The audit now reports a display with
a non-empty layout whose length is read while no instruction writes its
sequence (`display-length-unborn`). On `main`'s lowering of
`len((n, n + 1))` it reports that one finding.

The doc 33 note that the members' producer region is owned by a later
conditional did not reproduce at `main`: `t = (n > 0, n > 2, n > 4)` with
`if t[1]:` before `len(t)` returns Python's value after the birth
(observed).

**Corpus.** `c260_tuple_display_len` (bool and int tuples, unpacking,
iteration, a `t[1]` guard; loud at `main`) and `c261_tuple_len_silent`
(silently wrong at `main`, PASS now). Fuzz snippets: a computed tuple's
`len` and projection, and a loop over a bool tuple.

**What became loud instead of silent** (observed; each matches the list
form at `main`, so each is an existing frontier item, not a new one):
- a tuple rebound inside a loop: PRODUCT-REFUSES, as `xs = [i, i + 1]` in
  a loop does (C2);
- a nested tuple `((n, n + 1), (n + 2,))`: "no source cell" for the
  SEQUENCE_MUTATION block, as the nested list does (C6);
- a display that repeats a producer, `(m, m, 9)`: "lacks one exact element
  producer", as `[m, m, 9]` does (measured by the A0 thread);
- a member that projects another structural tuple, `(t[1], n, 9)`: the
  layout member is the Subscript's id while the `elts` edge names the
  forwarded producer (measured by the A0 thread; loud for lists too).

**New frontier finding, loud at `main` and here.** A helper returning a
tuple, `p = pair(n); len(p) + p[1]`, fails C compilation: the call's
aggregate pointer array is typed `double *` for `int64_t` members. This
belongs with B1 (return surface).

## 2. W2 closed: concatenations (four writers, one family)

W2 (found by the coverage march's fuzz snippets) was `d = {1: 5, 2: 4};
d[3] = n; xs = [1, 2] + [n, 8]`, after which `xs[2]` read 0. Minimizing it
showed four writers that each made a list concatenation wrong without an
audit finding. Three were silent at `main` (observed, scratch and corpus).

**1. Placement (c262).** The concat is a table region operation (reset,
then one `append_slice` per operand). Its region was placed where its
members start (`_member_completion_position`), so the `+` at column 9 sorted
before the `[n, 8]` display at column 18, whose birth (clear, appends) is
placed at its own start. With a dict store's region in the same function
the copy was observed to come first and read an empty `[n, 8]`. The A0
thread found the same writer independently (fuzzer p16_29, PR #786, commit
a4c29be9: a member reading a display operand completes where that display
ends). This branch carries that change verbatim instead of its own broader
rule, so the two PRs merge cleanly. Records: the display's birth
(`ssa_sequence_clear` of sequence 12) and the copy naming it
(`append_slice`, `source_sequence_id` 12), in that order in one block. The
audit now reports `display-read-before-birth` when a slice copy reads a
display before its birth in the same block (one finding on `main`'s
placement of c262's shape, 0 after).

**2. Row type (c264).** `xs = [1, 2] + [n, 8]; return xs[2]` returned
`3.0` (TYPE). The concat's arena has no writer but slice appends, so its
row stayed `unknown` and scalar settlement typed it float64 (trapped:
`_sequence_descriptor` → `external_value` mints `unknown`, then
`ir_indexing._propagate_scalar_dtypes` writes float64). Rule: a slice
append is a row writer; the source's row type refines the destination's,
as an append's stored value does (`_emit_sequence_append_slice`).

**3. Nested bounds (c263).** `ws = [n] + [1, 2] + [n * 2]` gave
`len(ws) == 2` for 4, and `ys = [7, 8] + xs; zs = ys + [n]` lost rows. The
capacity survey bounded a concat only when both operands carried
`aggregate_kind == "list"`; a concat (an `Add`) carries none, so a concat of
a concat had no bound and took the planner's elementwise extent. Rule: a
bounded concatenation is a list operand; the bounds settle to a fixed point.

**4. Unbounded concats.** `xs` grown in a loop, then `ys = [7] + xs`:
`len(ys)` read 1 for 4 at `main`. A concat no bound covers was neither
bounded nor DYNAMIC. Rule: a concatenation is born in its function and
holds its operands' rows; with no proven bound it is DYNAMIC. It is now
**loud**: `dynamic-growth-unavailable ... this operation must support arena
replacement`, because `append_slice` has no DYNAMIC growth protocol yet.
That is the new frontier item (a lowering, Lane C).

Fuzz snippets: the W2 shape (dict store beside a concat) and a three-way
concat.

## 3. C13 made loud: a list mixing int and float rows

**Program.** `ys = [n]; ys.append(n * 0.5); return ys[1]` and
`ys = [1 * n, 2.5 * n]; return sum(ys)` (lanes plan C13, found by Lane C).
At `main` the second returned 3.0 for 3.5 (n = 1). The first exported
nothing (`Ret []`). Both had 0 audit findings.

**Records that disagree.** The arena's row type is int64, taken from its
first row. The appended row's value is float64. The append helper's row
formal is int64, and the call input adapter
(`ssa_call_input_adapters`, the `logical_scalar_conversion` branch) minted a
float64 to int64 `Cast` (`concordant_call_input_conversion`) to make them
agree.

**Rule.** Python never converts a float to an int implicitly. A call input
conversion from a floating actual to an integer or bool formal is refused
by name (`call input conversion would truncate`). Widening conversions are
unchanged.

**Not lowered.** A list whose rows have different scalar classes needs a
per-row class (or a float64 arena plus the int rows' class) to be exact:
`ys[0]` must stay `int` while `sum(ys)` is `float`. That is a Lane C
lowering, still open. Test: `tests/test_mixed_row_list_refusal.py`.

## 4. C14 closed: a loop over an inline comprehension

**Program.** `for y in [x * n for x in xs]: t += y` with `xs` a folded
literal (c265) returned 0. It was silent at `main`, where the unrolled
comprehension had no birth at all.

This builds on Lane C's b1da6a5e (an unrolled comprehension over a folded
list is born like a display), which this branch carries unchanged. That
commit closed the named form (`ys = [...]; for y in ys`). The inline form
still read 0.

**Records that disagree.** The loop reads the iterable's length
(`resident_iterable_length`, sequence 11) in the entry block. The
comprehension's birth (clear, three appends) was installed in the loop
body.

**Writer.** `_install_lexical_sequence_mutations` kept a private copy of
loop containment, and that copy used the `for` statement's whole span. The
birth is authored on the `for` line, so the copy put it inside the loop.
The p3_46 rule (`_loop_body_line_span`: a `for` loop's iterations are its
body lines) existed but had not reached this copy.

**Rule.** There is one containment rule; this copy now calls it. The other
`loop.lineno <= line <= loop.end_lineno` tests sit in the capacity survey,
where they mark an append as loop-grown. A whole span is the conservative
direction there (a wrong guess makes the arena DYNAMIC, not short), so they
are unchanged.

Fuzz snippet: a loop over an inline comprehension of a literal.
